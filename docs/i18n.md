# Internationalisation

English and Portuguese, following the device, overridable in the app.

## Why the built-in one

Flutter's own `gen-l10n` rather than `slang` or `easy_localization`, for
reasons specific to this repo rather than a general verdict:

- **It adds no package.** `flutter_localizations` and `intl` were already in
  the tree as transitive dependencies of `serverpod_auth_idp_flutter`; adopting
  this promotes two entries and resolves nothing new.
- **It adds no generator.** The repo already carries two — riverpod_generator
  and theme_tailor, both on build_runner — and that is real debt. `gen-l10n`
  lives in the Flutter tool and fires on `flutter pub get`, so there is no
  third thing to schedule, watch, or remember.
- **Keys are checked at compile time.** `easy_localization` resolves them at
  runtime, so a typo becomes a missing string in front of a user instead of a
  failed build. In a repo that analyses with `--fatal-infos` that is a step
  backwards. (It also sits at 140/160 on pub points, against 160 for the
  alternatives.)
- **`slang` is the real contender** and loses on cost, not quality: a nicer API
  (`t.headline`, no `!`) for another dependency, another generator and another
  generated file shape.

The auth package turned out not to constrain the choice. Its sign-in widgets
take explicit text objects — `EmailSignInTexts` and friends — through an
`InheritedWidget`, so they are fed strings from whatever mechanism the app uses.

## Where it lives

| Path | Role |
|---|---|
| `l10n.yaml` | generator config: input dir, template, output class |
| `lib/l10n/app_en.arb` | the template, and the only file with `@` metadata |
| `lib/l10n/app_pt.arb` | the translation |
| `lib/l10n/app_localizations*.dart` | generated — never hand-edited |
| `lib/app/locale_controller.dart` | lets a user override the device |

## Adding or changing a string

Add the key to `app_en.arb` **with** a `description`, then to `app_pt.arb`
without one:

```json
"greetingCount": "{count, plural, =0{No greetings} =1{One greeting} other{{count} greetings}}",
"@greetingCount": {
  "description": "How many greetings came back.",
  "placeholders": { "count": { "type": "int" } }
}
```

`flutter pub get` regenerates. `required-resource-attributes: true` in
`l10n.yaml` means a key present in the template and missing from a translation
fails the build instead of silently falling back to English at runtime.

Read it as `AppLocalizations.of(context)!.greetingCount(3)`. The `!` is the
generator's ergonomics, not a choice — like `appTokens`, it throws if the app
was set up without the delegate, which is a misconfiguration rather than a
state to handle.

## Following the device, and overriding it

`MaterialApp.locale` resolves from the platform when it is `null`, so following
the device is the default and costs nothing. `LocaleController` holds a
`Locale?` where `null` means exactly that, and the app bar cycles
device → English → Portuguese → device.

This is the same shape as `ThemeModeController`, deliberately: both are
"follow the platform unless the user said otherwise", and neither persists the
choice, because that needs a storage dependency the app does not have yet.

The language names in the picker are each written in their own language —
`English`, `Português` — and are not translated. A picker that renders every
option in the language you are already reading is no use to someone who cannot
read it.

## Portuguese is `pt`, not `pt_BR`

The copy is Brazilian, but the file is `app_pt.arb` and the supported locale is
`pt`. Flutter resolves a locale by exact match first and then by language, so a
device set to `pt_BR` gets this file — and so does one set to `pt_PT`. Naming it
`pt_BR` would have sent every other Portuguese device to English, which is a
worse outcome than Brazilian spelling.

## What the tests pin

Widget tests pass `locale:` explicitly rather than inheriting the harness
locale, so the copy they assert on is not an accident of the machine. One of
them pins `pt` and asserts `Diga olá.`, which is the same mechanism the
in-app switch uses — proving the override without tapping a button.

The end-to-end suite asserts by key, never by copy. It is the one suite outside
`melos run check`, so anything it depends on that translation is free to change
would break it days later.
